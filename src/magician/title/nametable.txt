;   The title screen's tile grid -- 32 x 30, one row of 32 hex bytes per line.
;
;   THIS IS THE SOURCE. The packed .DAT that TITLE.SRC incbins is generated from
;   this file by tools/datcodec.py on every build (asm/build.py:pack_our_scenes)
;   and is never committed, so this grid is the only copy of the screen.
;
;   ------------------------------------------------------------------
;   HOW THIS LAYOUT WAS DERIVED -- by observing, not by copying
;   ------------------------------------------------------------------
;   1. THE SCREEN IS AN ASCENDING RUN OF TILE INDICES. Rows 4-26 climb from $00
;      to about $F2, with $08 wherever the picture wants the backdrop. That is not
;      a coincidence: the title artwork is stored in TIT0.CHR in exactly the
;      order the nametable consumes it, which is why 960 bytes that look like
;      noise pack into 281. It also means this file has to be read with
;      tools/scenerender.py, which draws it.
;
;   2. THE BLANK TILE IS $08, AND $00 IS NOT BLANK. TIT0.CHR has exactly one
;      all-zero tile, $08. Tile $00 has art -- it is part of the logo. Getting
;      this backwards fills the frame rows with a scrap of the artwork instead of
;      leaving them empty, and nothing complains.
;
;   3. THE CARTRIDGE FRAMES THE PICTURE WITH BLANK ROWS. A BizHawk run of the
;      cartridge at frame 60 (tools/bizhawk/title.lua, CIRAM nt0) has row 0 and
;      rows 27-29 entirely blank and the picture in rows 1-26. Eurocom's data
;      runs art from row 0 to row 28, so its picture bleeds off the top and
;      bottom edges. Rows 0 and 27-29 are blanked here to match.
;
;   Rows 4-26 are left where Eurocom's data puts them even though the cartridge
;   starts its picture at row 1. Moving ours up three rows would be wrong: the
;   attribute table is a fixed grid of 4x4 blocks tied to *screen* position, not
;   to the picture, so sliding the artwork three rows up slides it off its own
;   colour regions and recolours the logo. The blank band at the top is the price
;   of keeping the two aligned, and it is four rows rather than the cartridge's
;   one because the two artworks are different revisions -- see below.
;
;   ------------------------------------------------------------------
;   WHAT IS *NOT* REPRODUCED, AND WHY
;   ------------------------------------------------------------------
;   The cartridge's title screen is a different revision of the artwork. Its
;   TIT0/TIT1/TIT2.CHR share 87%/78%/54% of their 24-byte slices with ours, and
;   its packed scene descriptor has no 24-byte slice in common with ours anywhere
;   in PRG or CHR. So the composition here is the one our art supports: the
;   MAGICIAN logo, the brick field, the figures, the moon. The cartridge also
;   has "- EUROCOM ENTERTAINMENT SOFTWARE PRESENTS -" across the top and
;   "LICENSED BY Nintendo / (C)COPYRIGHT TAXAN USA CORP. 1990" along the bottom.
;   Those tiles are not in our CHR bank; naming them would name tiles that do not
;   exist, which is the silent failure tools/titletest.py exists to catch.
;
;   Rows 28-29 sit at $2380-$23BF and are ordinary tile bytes, so they are
;   displayed -- blanking them is a real change to the picture, not a no-op.
;
;   Tile indices are 8-bit and address TIT0.CHR, the first 4 KiB bank of the
;   title set (TIT0/1/2.CHR sit contiguously at CHR $E000/$F000/$10000).
